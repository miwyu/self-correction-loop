# 自己修正ループ (Self-Correction Loop)

「終わりました」という報告を確かめてみたら、終わっていなかった。
Claude にタスクを任せたことがあれば、身に覚えのある展開だと思います。
このスキルは、その「終わりました」を作業者本人に言わせないための Claude Code スキルです。
作業を**自己修正ループ**として構造化し、ルーブリックと成果物だけを渡された**独立した検証者**（verifier）のサブエージェントが全基準を満たしたと確認するまで、反復を続けます。

## なぜ作ったか

出発点は、現在のモデルについての二つの観察です。

一つめ。**モデルはフィードバックに対してヒルクライムすると着実に改善します。**
チェック可能なゴール（テストスイート、スコアラー、ルーブリック）さえあれば、実行して、計測して、調整して、また実行する、というループを回せます。
難しいタスクでは、このループはワンショットのプロンプティングを上回ります。

であれば、ループを回させて、最後に自分でチェックさせれば済みそうなものです。
ところが、そこに二つめの観察が立ちはだかります。
**モデルは自分の成果物の採点が苦手です。**
作業を終えたモデルは、成果物そのものではなく自分の意図に引きずられるため、自己批評は早めに勝利を宣言しがちです。
同じモデルでも、別のコンテキストウィンドウで採点させると、つまりルーブリックと成果物だけを見て作業者の思考過程は一切見ない検証者サブエージェントに任せると、判定は格段に信頼できるものになります。

このスキルは、両方の観察を再現可能な手順にまとめたものです。
ただし、こうしたループには固有の失敗モードがあります。
指標のゲーミング、すなわちテストの弱体化、スコアラーの改変、期待出力のハードコードです。
「テストが通るまで」と指示されたモデルにとっては、コードを直すのもテストを緩めるのも同じ一手だからです。
そこでこのスキルでは、保護ファイルを作業開始前に固定し、機械的に照合するガードレールを入れています。
また、作業はあなたのチェックアウトの外に隔離されます。
ループは使い捨ての git worktree（未コミット変更への dirty-state ガード付き）の中で実行され、worktree が使えない環境では `.loop/` ディレクトリにフォールバックします。

## どんなときに使うか

**完了の定義が計測可能**で、一発では解けそうにないタスクに使います。

- 「テストが全部通るまでループして」
- 「このベンチマーク/スコアラーが 100 になるまでヒルクライムして」
- 「ルーブリックを満たすまでこのドキュメントを改善して」

逆に、ワンショットで済むタスクに使うと損をします。
ループのオーバーヘッド（私たちのベンチマークでは実時間でおよそ 2〜4 倍、大半は検証者サブエージェント）は、客観的に収束できる対象があって初めて元が取れるからです。
チェック可能なゴールを立てられないタスクも同様です。

## ループの仕組み

```
0. 隔離
   使い捨ての git worktree の中で作業する — worktree が使えない場合は
   .loop/ ディレクトリ — ループがチェックアウトを汚さないようにする
        ↓
1. ルーブリック作成
   verbatim テンプレートを穴埋めする: 1 行の CHECK コマンド
   (exit 0 = 合格)+ 作業開始前に sha256 で固定した保護ファイル一覧
        ↓
2. ベースライン
   まず誠実に 1 回試行し、開始時点の計測値を EXPERIMENTS.md に記録する
        ↓
3. 反復
   変更は一度に 1 つ → 軽いチェックを実行 → 記録
   (CHANGE/WHY/RESULT/DECISION)。
   3 iteration 改善が無ければ微調整ではなく構造的な賭けに切り替える
        ↓
4. preflight + 検証
   scripts/preflight.sh が exit 0 になること(書式がパースでき、ガードが
   成立し、全 CHECK が通る)— その後、verbatim プロンプトテンプレートから
   フレッシュなコンテキストの検証者サブエージェントを起動する
        ↓
   FAIL の場合 → その evidence を入力として 3. に戻る
   PASS の場合 ↓
        ↓
5. 停止
   検証者の OVERALL: PASS が出たときのみ停止する。明示的な予算に達した
   場合は、暫定ベストと実験ログを報告して停止する
```

手順を散文で渡すだけだと、弱いモデルは途中でドリフトします。
そこで、機械的な部分はスクリプトに降ろしてあります。
`scripts/check_guards.sh` はルーブリックに記録された sha256 アンカーと保護ファイルを照合し、`scripts/preflight.sh` は書式検査と CHECK コマンド検証で検証者の手前にゲートを置きます。
ルーブリック、実験ログ、検証者プロンプトの書式は `references/` の verbatim テンプレート（プレースホルダのみ置換）で決まっており、設計理由は `references/rationale.md` にあります。

各実行は監査証跡を残します。
ガードを含む「完了」の定義（`RUBRIC.md`）、全試行とその計測結果（`EXPERIMENTS.md`）、そして検証者による基準ごとの判定です。
いずれもあなたのチェックアウトの外、worktree または cwd の `.loop/`（`.git/info/exclude` で除外）に置かれます。
成功時の報告にはブランチ、diff 要約、マージ手順が含まれ、失敗時は worktree が検証用にそのまま残ります。

スキルの完全な指示は [self-correction-loop/SKILL.md](self-correction-loop/SKILL.md) にあります。

## このリポジトリについて

このリポジトリはスキルの開発プロジェクトで、skill-creator の評価ループ（テストプロンプトをスキルあり/なしで実行し、アサーションで採点し、レビューして改訂する）で反復開発しています。

- `self-correction-loop/`：スキル本体
- `evals/`：ベンチマーク用のテストケースとフィクスチャ
- `self-correction-loop-workspace/`（gitignore 対象）：生成された実行結果

開発ワークフローとベンチマークコマンドは [CLAUDE.md](CLAUDE.md) を参照してください。
